# Upstream

How KnotGate stays a cheap downstream of Wolfgate. This covers the layer, the tooling that checks it, merging Wolfgate
in, and the rules that keep two codebases safe on one database. Wolfgate carries none of this: KnotGate treats
Wolfgate the way Wolfgate treats Monolith.

## The layer

- Prefix `_KG`, marker `KNOTGATE`, IDs prefixed `KG`. The folders are the table in AGENTS.md with `_KG` in place of
  `_WG`.
- `Tools/_KG/Ci/modules.py` is KnotGate's copy of Wolfgate's `Tools/_WG/Ci/modules.py`, made layer-aware. Its
  config, `Tools/_KG/Ci/modules.yml`, sets:
  - the layer: `layer.prefix` and `layer.marker`;
  - the paths closed to it: `layer.forbidden`;
  - `fork_point`, the Wolfgate commit KnotGate is based on. Lines that match Wolfgate at that commit count as
    upstream code and need no marker.
- CI (`wg-modules.yml`) runs three checks: Wolfgate's `--check`, which must stay clean, then KnotGate's `--check`
  and `--pr-check`. Wolfgate's own `--pr-check` is off here, because KnotGate's edits carry KNOTGATE markers.
- Builds publish to the CDN fork `knotgate`. Day to day, the SSymphony panel builds on the box and publishes there
  with that fork's token.

## Rules

- **Wolfgate is upstream, `_WG` included.** An edit to any Wolfgate file carries a KNOTGATE marker, under the same
  rules as a Wolfgate edit to Monolith code. Never add WOLFGATE markers or new files under `_WG`.
- **Prefer, in order:**
  1. a setting in KnotGate's `server_config.toml`;
  2. a new prototype or system in `_KG`;
  3. a marked edit.

  Most PvE switches already exist as Wolfgate cvars (`wg.encounters.*`, `wg.sector.enabled`, `wg.defcon.enabled`,
  `wg.ship_squatters`, ...).
- **Keep edits to Wolfgate files small** and inside marked blocks, so Wolfgate merges stay mechanical.

## Merging Wolfgate in

1. `git fetch wolfgate` (remote `https://github.com/VanguardControl/Wolfgate.git`). Make a branch `upstream/<date>`
   from KnotGate's `main`, then run `git merge wolfgate/main`.
2. Resolve conflicts; they come from KNOTGATE-marked edits. If Wolfgate changed `Tools/_WG/Ci/modules.py`, port
   the change into `Tools/_KG/Ci/modules.py`.
3. Regenerate the docs: `python Tools/_WG/Ci/modules.py --write`, then `python Tools/_KG/Ci/modules.py --write`.
4. Move `fork_point` in `Tools/_KG/Ci/modules.yml` to the merged Wolfgate commit.
5. Open the pull request with a title starting `[UPSTREAM]`. The layer's edit check skips it.

When Wolfgate ships a migration, merge it promptly: it is already live on the shared database.

## The shared database

KnotGate and Wolfgate use one PostgreSQL database for characters, bank balances, bans, playtime and the whitelist.

- **No migrations in KnotGate.** `layer.forbidden` makes the pull request check fail on any file under
  `Content.Server.Database/Migrations`. Schema changes are Wolfgate's to make. KnotGate merges them after Wolfgate
  deploys them.
- **KnotGate can run a little behind.** Wolfgate's build deploys its migration first, so for a while KnotGate runs
  on a newer schema than its code expects.
  - Additive migrations (nullable or defaulted columns) are safe.
  - If Wolfgate renames or drops a column, merge that release into KnotGate before restarting it.
- **Don't disable saved content.** Both servers load the same profiles. These hold species, markings, traits,
  loadouts, jobs, companies and consent keys. If KnotGate turns one off, a player who saves here loses it, and the
  loss shows on Wolfgate too. KnotGate-only content of that kind needs Wolfgate to carry it.
- **Each server names itself** with `[adminlogs] server_name`, so rounds and admin logs show where they happened.
- **Staged:** KnotGate starts on `wolfgate_test`, beside the Wolfgate test server, and moves to `wolfgate` later.

## What would need Wolfgate

Only a Wolfgate change can give KnotGate these cleanly, if they're ever wanted upstream:

- a switch for faction-locked shipyard vessels;
- a switch for mobs on NF salvage expeditions;
- a master switch for WG Companies;
- the layer-aware `modules.py`, so KnotGate doesn't have to carry its own copy.
